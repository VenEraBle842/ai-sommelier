# Воспроизводимая офлайн-оценка

Из корня репозитория, без сети, ключей, сервера и изменения рабочей базы:

```bash
uv sync --locked
uv run python -m app.evaluation
uv run python -m app.evaluation --output /tmp/svoevino-evaluation.json
uv run pytest
uv run ruff check .
uv run ruff format --check .
uv run mypy
node tests/test_ui_messages.mjs
```

Команда печатает JSON; `--output` дополнительно сохраняет тот же JSON, заменяя
содержимое указанного файла. `--k 1..5` меняет максимальную длину итоговой выдачи
(по умолчанию 3). Код завершения 0 означает прохождение ожиданий сценариев и
проверок персонализации; 1 — несовпадение с эталоном либо ошибку данных/записи.
Это не порог качества всех метрик: например, Food Match может быть ниже 100%.

## Снимок и эталон

`app/evaluation/data/snapshot.json` перечисляет **три реальные карточки**,
их URL и SHA-256 сохранённых HTML. HTML скопирован без изменений из реальных
фикстур `tests/fixtures`; происхождение описано в `tests/fixtures/README.md`.
Это сокращённые страницы, сохранённые 19 октября 2026 года, а не весь каталог.
Временная отметка 00:00 UTC — техническая фиксация даты снимка для повторяемости,
а не известное время сетевого запроса. Новые загрузки в этой оценке не происходят.

При каждом запуске HTML проверяется по SHA-256 и штатным детерминированным
парсером преобразуется в записи отдельной временной SQLite. Она удаляется после
прогона. `WINE_DB_PATH`, рабочая история и настройки внешней модели игнорируются.
Снимок никогда не загружается в рабочую базу при запуске приложения.

`scenarios.json` содержит **24 сценария** с независимыми ожидаемыми свойствами:

- 20 проверяют текстовый запрос через ограниченный резервный парсер;
- 4 проверяют движок на явно заданном `UserIntent`, минуя извлечение из текста;
- 4 сценария задают ожидаемые реальные сочетания с едой;
- 1 проверяет честную обработку бюджета без цен;
- 1 сравнивает результат до и после лайка; ещё 1 проверяет, что история не
  возвращает понравившееся красное вино при обязательном белом цвете.

Структурированные сценарии помечены в отчёте: их нельзя считать оценкой понимания
естественного языка. Ожидания записаны вручную по полям реальных карточек,
не генерируются текущим ранжировщиком. `acceptable_slugs` задаёт допустимые
реальные позиции, когда одного набора ограничений недостаточно. Slug связывается
с ID временной базы; полный манифест ID/URL/контрольных сумм включён в отчёт.
Это не обещание одинакового ID в произвольной рабочей базе.

## Определения метрик

Все доли в JSON находятся в диапазоне 0..1. `N/A` означает нулевой знаменатель.
`denominators` и `hard_constraint_by_dimension` показывают числа наблюдений.
Единица наблюдения — рекомендация, поэтому одна карточка может участвовать
несколько раз в разных сценариях.

| Поле | Как рассчитывается |
| --- | --- |
| `hallucination_rate` | Число выданных ID, отсутствующих в репозитории, / число всех выданных рекомендаций |
| `catalog_validity` | Число выданных ID, найденных в репозитории, / число всех рекомендаций |
| `hard_constraint_accuracy` | Рекомендации, удовлетворяющие всем оцениваемым явным условиям эталона, / рекомендации со хотя бы одним оцениваемым условием |
| `hard_constraint_by_dimension` | Доля соблюдения отдельно для цвета, сладости, всех требуемых сортов, допустимого региона, производителя, категории и известной цены |
| `food_match_rate` | Рекомендации с хотя бы одним ожидаемым реальным `food_pairings` / все рекомендации в сценариях с едой |
| `hit_rate_at_k` | Сценарии, где хотя бы одна из первых K рекомендаций одновременно удовлетворяет ожидаемым свойствам, / положительные сценарии с оцениваемым эталоном |
| `scenario_success_rate` | Сценарии с ожидаемым статусом и допустимым результатом / все сценарии, включая уточнения и ожидаемое отсутствие кандидатов |
| `factual_field_accuracy` | Карточки ответа, полностью равные повторно прочитанным записям репозитория, / все рекомендации |

Неизвестный ID остаётся в знаменателях валидности и применимых ограничений
как ошибка. Пустая выдача в положительном сценарии — промах HitRate, а не
идеальное соблюдение условий. При отсутствии рекомендаций метрики по карточкам
возвращают `N/A`. Ожидаемое отсутствие кандидатов и уточнение проверяются через
успех сценариев, но не повышают HitRate.

Оракул ограничений в `metrics.py` сравнивает поля самостоятельно: он не вызывает
рабочие `matches_constraints`, ранжировщик или проверку вкуса. Истина о карточках
берётся из SQLite, а не из скопированных полей ответа. Отдельные тесты подают
испорченные ответы, неизвестные ID и нарушенные условия: метрики действительно
падают и не являются константами.

### Бюджет

В реальном снимке **нет ни одной подтверждённой цены**. Поэтому бюджетная
точность — `N/A`, а не 100%. Неизвестная цена исключается только из бюджетного
измерения; цвет и другие известные свойства продолжают оцениваться.
`unknown_budget_excluded` показывает число таких исключений.

Сценарий неизвестного бюджета проверяет `budget_constraint_unavailable` и
`budget_satisfied = null`. Он не входит в HitRate: гарантировать бюджет нельзя.
При известной цене оракул проверяет `price_rub <= budget_max_rub`; неизвестная
цена никогда не считается бюджетным попаданием. Известные/слишком большие цены
проверяются отдельными **искусственными граничными случаями во временной тестовой
базе**, без изменения реального снимка или выдачи их за цены магазина.

### Персонализация

Один и тот же запрос «Белое сухое» выполняется до и после сохранения лайка
реальному «Шенен Блан. Бетон. Дрозд» через `UserRepository`. Проверяются рост
балла, положительный компонент `personalization` и отсутствие ухудшения позиции.
Профиль строится штатным `PreferenceProfile`. Для базового сравнения доступны
до пяти кандидатов независимо от K; итоговый персональный ответ ограничен K.
Дополнительный базовый ответ не включён в число рекомендаций основных метрик.
Само наличие лайка не гарантирует успех: направление изменения вычисляется
из двух фактических ответов. Для каждого сценария используется отдельный UUID.

## Измеренный результат

Полный воспроизводимый отчёт текущего запуска: `evaluation-results.json`.
При K=3 на 24 сценариях / 3 реальных винах получены:

- 24 рекомендации; валидность 24/24, галлюцинации 0/24;
- соблюдение оцениваемых обязательных условий 23/23;
- Food Match 4/6 (66,7%);
- HitRate@3 16/16 положительных сценариев с оцениваемым эталоном;
- ожидаемое поведение сценариев 24/24; фактические поля из SQLite 24/24;
- персонализация 1/1: ID 2 поднялся со второго места на первое, балл 0 → 6;
- бюджетная точность `N/A`: 0 наблюдений с подтверждённой ценой.

**Food Match ниже 100%:** в запросах к рыбе и десерту первая карточка имеет
нужное сочетание, а вторая совпадает только по обязательным цвету и сладости.
Текущие правила допуска это разрешают. HitRate@3 этого недостатка не отражает,
поскольку измеряет хотя бы одно попадание. Результат сохранён без подгонки
данных или изменения правил подбора ради метрики.

Это ограниченная инженерная оценка на маленьком снимке. Она не измеряет
субъективное удовольствие от вина, покрытие всего сайта, реальное качество
внешней модели, актуальные цены или скорость на большом каталоге. Нельзя
называть её «точностью системы 100%». При расширении снимка нужно обновлять
манифест, независимые ожидания и сохранённый отчёт одним проверяемым изменением.

## Внешняя модель и устойчивость

Офлайн-команда не создаёт LLM-клиент и не читает его настройки. Реальные API
в автоматических тестах запрещены общей фикстурой блокировки сокетов.
Отдельные проверки в `test_llm_client.py`, `test_recommendation.py`,
`test_product_api.py` и `test_evaluation.py` используют `FakeLLM` и
`httpx.MockTransport`: правильный JSON, ошибочный JSON, тайм-ауты, неизвестные ID,
подмена фактов и сбой объяснений. Это проверка протокола и инвариантов, а не
LLM-as-a-judge и не оценка качества конкретного внешнего сервиса.

## Небольшая проверка скорости

На текущей машине выполнено 50 последовательных запросов, попеременно
«Красное сухое к стейку» и «Белое сухое к рыбе», с теми же тремя реальными
карточками в SQLite в памяти, без внешней модели. Измерялся весь вызов
`RecommendationService.recommend`, включая чтение и повторную проверку карточек:
медиана 3,354 мс, p95 8,492 мс (48-е значение отсортированных 50 измерений).
Это разовая локальная проверка малого снимка, не HTTP-бенчмарк, не измерение
дисковой базы и не обещание производительности на большом каталоге.
Время намеренно не включено в детерминированный JSON основных метрик.
