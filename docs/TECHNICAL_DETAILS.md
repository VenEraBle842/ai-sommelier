# Технические подробности локального MVP

MVP: реальный HTML-каталог &rarr; детерминированный парсер &rarr; SQLite &rarr; подбор вина.
Рекомендации рассчитываются Python; внешняя текстовая модель может разбирать
пожелания и помогать с объяснением. Оценки пользователя сохраняются в SQLite
и влияют на порядок подходящих вин.

Нужны Python 3.14 и [uv](https://docs.astral.sh/uv/). Зависимости зафиксированы
в `uv.lock`. Выполняйте команды из корня проекта:

```bash
uv sync --locked
uv run python -m app.catalog.sync --pages 2 --limit 30
```

База `data/catalog.sqlite3` и её папка создаются автоматически. В рабочей базе
нет искусственных вин: её наполняет только отдельная синхронизация с
https://vino-svoe.ru/wines. Для синхронизации нужен доступ в интернет.
Повторный запуск обновляет поля и дату загрузки, сохраняя локальный `id`.

```bash
uv run python -m app.catalog.sync --help
uv run python -m app.catalog.sync --pages 1 --limit 3 --db data/проверка.sqlite3
uv run uvicorn app.api.main:app --log-level warning
```

API: `GET /wines?limit=50&offset=0` и `GET /wines/{wine_id}` на
http://127.0.0.1:8000. API читает только локальную базу и не обращается к сайту.
По этому же адресу `/` открывается интерфейс винного гида. Сборка фронтенда
не нужна: Jinja2, локальные CSS и JavaScript поставляются с приложением.
`WINE_DB_PATH` задаёт другой путь базы для API и синхронизации; `--db` имеет
приоритет для команды. Схема API доступна по `/openapi.json`.

Проверки выполняются без сети:

```bash
uv run pytest
uv run ruff check .
uv run ruff format --check .
uv run mypy
```

В `tests/fixtures/README.md` указано происхождение сохранённых фрагментов HTML.
Тесты проверяют поля реальных карточек, отсутствие выдуманных данных,
повторную синхронизацию, ограничения обхода, сетевые сбои и чтение API.

## Границы текущего этапа

- Цена не подтверждена: `price_rub` всегда `None` без отдельного доверенного
  `PriceProvider`. Парсер игнорирует любые ценоподобные числа. Без подтверждённых
  цен соответствие бюджету не гарантируется. При наличии цен движок применяет
  строгий бюджетный фильтр, исключая позиции с неизвестной стоимостью.
  Тестовый поставщик цен используется только в тесте.
- Крепость и температура сохраняются строками: исходные диапазоны не усредняются.
  Цвет и сладость нормализуются по известным значениям; исходная категория и
  оттенок сохраняются отдельно. Неизвестное значение не угадывается.
- Рейтинг берётся только из явно подписанного народного рейтинга карточки,
  в диапазоне 0–5. Пустые поля остаются `None` или пустыми списками.
- Загрузчик последовательный: тайм-аут 20 секунд, пауза не меньше секунды,
  два повтора временных сетевых ошибок с увеличением задержки. Учитываются
  robots.txt и `Crawl-delay`. HTTP 401/403/429, CAPTCHA, перенаправление и
  `Retry-After` прекращают запуск; обхода ограничений нет.
- `--pages` ограничивает страницы (по умолчанию 1000), `--limit` — попытки
  загрузки уникальных карточек, включая неудачные. Ошибка отдельной карточки
  не мешает другим; итоговый код при ошибках — 1. Прерывание — 130.
  Уже сохранённые карточки остаются в базе.
- Синхронизация перечитывает выбранные карточки и обновляет их через upsert;
  условные HTTP-запросы пока не используются. Удалённые с сайта записи
  автоматически не удаляются. Миграции схемы пока не реализованы.
- Парсер зависит от текущих CSS-классов сайта. Ошибка структуры каталога
  останавливает обход, неполная карточка без названия не сохраняется.
  Доступность сайта проверяется отдельно от автономных тестов.

В проекте нет локальных моделей, эмбеддингов, векторной базы и облачного
развёртывания.

## Подбор вина и внешний текстовый API

Рабочий конвейер:

```text
Русский текст и контекст прошлого шага
→ извлечение предпочтений и локальная проверка Pydantic
→ обязательные фильтры Python
→ детерминированные баллы
→ допуск по совпадению с запросом без учёта одного лишь рейтинга
→ не более пяти реальных Wine ID
→ повторное чтение фактических карточек из SQLite
→ необязательный выбор подтверждённых причин через LLM
→ проверенный ответ
```

Модель не получает весь каталог, не создаёт `Wine` и не выбирает позиции.
Ей передаются список существующих гастрономических категорий при разборе
и небольшой список уже выбранных ID с подтверждёнными причинами при объяснении.
Названия, производители, регионы, сорта, цены, ссылки и рейтинги в итоговом
ответе всегда берутся из репозитория. Неизвестные ID и причины отвергаются;
повторённые моделью фактические поля игнорируются.

Объяснение собирается из русских формулировок, подтверждённых полями каталога.
LLM может выбирать релевантные `reason_ids`, но не дописывать произвольные
дегустационные заметки, цены или награды. При ошибке остаётся объяснение Python.

Для внешнего API скопируйте `.env.example` в `.env` и заполните:

| Переменная | Значение |
| --- | --- |
| `LLM_API_KEY` | Секретный ключ выбранного совместимого сервиса |
| `LLM_MODEL` | Имя доступной у этого сервиса текстовой модели |
| `LLM_BASE_URL` | HTTPS-адрес совместимого API с базовым путём; клиент добавляет `/chat/completions` |
| `LLM_TIMEOUT_SECONDS` | Необязательный тайм-аут: по умолчанию 20 секунд, максимум 120 |

```bash
uv run --env-file .env uvicorn app.api.main:app --log-level warning
```

Имя коммерческого поставщика не задаётся. Ключ, модель и адрес не зашиты в
бизнес-логику. `.env` игнорируется Git; не добавляйте секретный ключ в репозиторий.
Файл `.env` загружает uv при использовании `--env-file`; само приложение читает
переменные окружения. Незаданные параметры отключают внешнюю модель.
Частичная или неверная конфигурация включает ограниченный локальный разбор.

Поддерживается минимальный HTTP-интерфейс `POST /chat/completions` с `model`
и `messages`. Ожидается JSON в `choices[0].message.content`; специальные
возможности структурированного вывода сервера не требуются. Ошибочный JSON
проверяется повторно не более одного раза, HTTP-ошибки и тайм-ауты приводят
к локальному разбору. Реальная совместимость конкретного сервиса зависит
от поддержки этого интерфейса; тесты не расходуют внешний API.

`POST /recommendations` принимает JSON:

```json
{"message": "Красное сухое к стейку до 2000 рублей", "limit": 3}
```

Ответ содержит `status`, русское `message`, проверенный `intent`,
`recommendations`, `budget_status`, `warnings` и `extraction_source`.
В рекомендации доступны фактическая карточка `wine`, её `wine_id`,
`score`, `breakdown`, `reasons`, `explanation` и `budget_satisfied`.
Если цен нет, `budget_status` равен `budget_constraint_unavailable`,
`budget_satisfied` остаётся `null`, а предупреждение объясняет ограничение.
Если в каталоге есть подтверждённые цены, бюджет применяется строго ко всем
кандидатам; неизвестная цена не удовлетворяет бюджету даже при совпадении
остальных обязательных условий.

Для продолжения диалога передайте полученный `intent` как `previous_intent`
в следующем запросе. Например, после вопроса о сладости отправьте сообщение
«сухое к стейку» с предыдущим контекстом. Непустые новые значения заменяют
предыдущие значения того же поля; остальные требования сохраняются.
Чтобы начать новый подбор, не передавайте `previous_intent`.
Сервер не хранит историю диалога и не требует фоновых служб.

Интерфейс использует `POST /chat`: те же поля, что у `/recommendations`, плюс
`user_id` — UUID, создаваемый и сохраняемый браузером. Для уточнения передаётся
`previous_intent`; после успешной подборки следующий запрос начинается заново.
Кнопка «Начать новый подбор» очищает условия, но сохраняет оценки.

`POST /feedback` принимает `user_id`, `wine_id` и `event_type`: `like`, `dislike`
или `opened`. Показы `shown` сохраняются сервером после подбора. История доступна
через `GET /users/{user_id}/history?limit=50` (максимум 200 последних событий).
`GET /health` проверяет SQLite и сообщает размер каталога, не вызывая внешнюю модель.

Новая таблица `user_events` создаётся автоматически рядом с `wines` без изменения
каталожных записей. Только последняя оценка каждого вина участвует в профиле:
повторный лайк не усиливает симпатию, дизлайк заменяет лайк. Показ и открытие
не меняют предпочтения. Учитываются цвет, сладость, сорта, регион, производитель,
реальные сочетания с едой и подтверждённые вкусовые признаки. Веса находятся в
`app/users/preferences.py`; общий вклад истории ограничен диапазоном −6…+6.
Он отображается отдельной строкой в разборе балла. История меняет порядок только
среди вин с подтверждённым совпадением с запросом и не даёт допуска сама по себе.
Обязательные условия и строгая проверка подтверждённых цен выполняются раньше.

Регистрации и защиты истории учётной записью нет: UUID — локальная идентичность
для демонстрации. Не открывайте сервер во внешнюю сеть. Очистка хранилища браузера
теряет связь с прежней историей; другой браузер получает независимый профиль.

Обязательные условия находятся в `hard_constraints`, пожелания — в
`soft_preferences`. Цвет, сладость, производитель и исходная категория
сравниваются точно после нормализации регистра, пробелов и ё. Все сорта
из обязательного списка должны присутствовать; регионы и исходные категории
в списках означают допустимые альтернативы. Неизвестное значение поля
не считается совпадением. При отсутствии кандидатов ограничения не ослабляются.

Веса собраны в `app/recommendation/ranking.py`: сочетание с блюдом — 10,
вкусовое упоминание и предпочитаемый сорт — 3, остальные предпочтения — 2,
народный рейтинг — 0,2 за балл. Явное упоминание нежелательного свойства
снижает оценку на 4. Равенство разрешается по постоянному локальному
ID. Вкусовые признаки определяются только по упоминаниям в исходном описании;
в обоснование включается буквальная цитата. Это не полноценный семантический
анализ: отсутствие упоминания означает неизвестность, а не отсутствие свойства.

`limit` — максимум, а не обязательное число позиций. До TOP-N отбрасываются
кандидаты без смыслового совпадения: блюда, вкуса, мягкого предпочтения или
явно заданных обязательных характеристик. Рейтинг и само присутствие в каталоге
не дают допуска. Если релевантных вин меньше лимита, ответ короче; при их
отсутствии возвращается `no_candidates`. Допуск проверяется повторно при чтении
фактической карточки перед ответом.

`dish` сохраняет исходное описание блюда с соусом и гарниром отдельно от
`normalized_food_categories`. В ответе LLM резервный парсер не заменяет полное
блюдо отдельным словом и не заполняет пустой список категорий. Для обычных
формулировок после «к», «под», «для» исходная фраза также восстанавливается
из сообщения. Категории проверяются по текущей SQLite; для узнаваемых основных
ингредиентов применяется консервативная проверка совместимости. Например,
птица не подменяется мясом и стейками, а соус не считается основным блюдом.
Несуществующие и явно неподходящие категории исключаются без подстановки
«ближайшей». Эта проверка использует ограниченный словарь, а не полный
семантический анализ русской кухни.

Положительные пожелания к вину находятся в `taste_preferences`: к прежним
восьми группам добавлено `насыщенное`. В источнике проверяется упоминание
насыщенного/интенсивного вкуса, плотного/полного тела либо полнотелости.
Интенсивность аромата, насыщенность цвета, кислотность, сладость, танины,
фруктовость, свежесть и мягкость сами по себе не подтверждают этот тег.
Среднее тело также не считается подтверждением полнотелости. Правила требуют
явной связи признака со вкусом или телом, сохраняют буквальную цитату источника
и не выводят одно свойство из другого. Словарь ограничен: неподдерживаемые
формулировки могут остаться без совпадения.
Положительный вкусовой признак может дать допуск к рекомендации без совпадения
по еде. Если такого подтверждения нет, выдача не заполняется по рейтингу.

Отрицательные пожелания представлены отдельным необязательным списком
`negative_taste_preferences`, по умолчанию пустым. Сейчас поддерживается
значение `грубая терпкость`: избегание грубой терпкости/жёстких танинов,
а не любых танинов. Пример проверенного намерения:

```json
{
  "dish": "утка с ягодным соусом",
  "normalized_food_categories": [],
  "taste_preferences": ["насыщенное"],
  "negative_taste_preferences": ["грубая терпкость"]
}
```

Пустая категория еды не очищает вкусовые пожелания. При извлечении свойства
соуса и гарнира отделяются от свойств желаемого вина: ягодный соус сам по себе
не означает запрос ягодного вина. Резервный парсер распознаёт только ограниченные
формы прилагательных и явные обороты избегания, не пытаясь заменить LLM.

Штраф за нежелательное свойство начисляется только по буквальному подтверждению
из описания. Если подтверждения нет, балл не меняется: это неизвестность,
а не доказательство отсутствия свойства. Само избегание и рейтинг не дают
допуска к выдаче. Штраф мягкий и не заменяет обязательные фильтры; вино с другими
подтверждёнными совпадениями может остаться в выдаче с явным предупреждением
в объяснении. LLM не может скрыть это предупреждение или оговорку о неизвестности.

Без модели поддерживается намеренно небольшой словарь: цвета, сладость,
числовой максимум бюджета, названия сортов, регионов и производителей из
локальной базы, стейк, мясо, рыба, лосось, сыр, десерт, птица, девять положительных
вкусовых групп и избегание грубой терпкости. «Выберите сами» отключает уточнения, но не проверку релевантности:
без других пожеланий это не повод возвращать вина только по рейтингу.
Неизвестные важные слова, неоднозначности и исключения вроде «без дуба»
не угадываются: возвращается просьба переформулировать запрос. Это ограниченный
резервный режим, а не замена пониманию естественного языка внешней моделью.

Тесты используют `FakeLLM` и `httpx.MockTransport`, очищают настройки LLM
из окружения и блокируют реальные сетевые соединения. Они проверяют ограничения,
ранжирование, уточнения, бюджет, недостоверные ответы, неизвестные ID и инвариант:
каждая рекомендация существует в репозитории и содержит именно его фактические поля.

## Офлайн-оценка

```bash
uv run python -m app.evaluation
uv run python -m app.evaluation --output /tmp/svoevino-evaluation.json
```

Команда использует отдельную временную SQLite и фиксированный снимок из трёх
реальных карточек, без сети и изменения рабочей базы. Набор содержит 24 сценария;
это не оценка всего каталога или качества внешней модели. Определения метрик,
знаменатели и ограничения: [методика оценки](EVALUATION.md).
[Проверка безопасности и устойчивости](SECURITY_REVIEW.md) описывает
проверенные границы локального MVP.
